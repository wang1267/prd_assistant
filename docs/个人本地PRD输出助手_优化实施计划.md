## 1. 产品定位与目标

**定位**：本地优先的个人 PRD 输出助手。帮助用户把模糊想法或已有文档，转化为可评审、可研发、可测试、可导出的需求包。

**核心闭环**：

```text
想法 / 导入现有 PRD
  → AI 动态访谈
  → 产品方案骨架确认
  → 结构化生成 PRD
  → 规则体检 + AI 证据型审查
  → 按问题优化并复核
  → 导出评审、研发、测试交付包
```

**明确不做**：账号体系、实时协作、成员权限、@提醒、任务中心、甘特图、第三方项目管理工具双向同步。

**留存定义**：完成激活（首次 10 分钟内创建/导入并处理至少一项问题）的用户，在 30 天内再次完成生成、检测、优化或导出 PRD 的比例。

## 6. 阶段 3：面向小白的 AI 需求澄清与 Vibe Coding 前置文档

**目标用户修正**：核心用户不假定是专业产品经理，而是准备开始 Vibe Coding 的小白。他们通常只能说清“想做什么”，不熟悉指标、优先级、边界、验收和数据埋点等术语。AI 的职责是把自然语言愿望转译为可确认、可生成、可交给 Coding Agent 的需求文档，而不是让用户填写专业 PRD 表单。

**对话原则**：先问用户能直接回答的问题（“谁会用”“现在怎么解决”“希望它帮你完成什么”“最不能接受什么”），再由 AI 推导专业字段；只有在确实影响方案选择时，才以解释和选项的形式询问指标、权限、数据或技术约束。任何 AI 推导必须显示为“AI 假设”，用户可一键确认、修改或跳过。

### 3.1 动态需求访谈

- [x] 从一句想法或口语化描述开始，不要求用户先填写指标、优先级或 PRD 字段。
- [x] 基于缺口动态追问：先澄清用户、现状、想完成的事、最小可用范围和不能接受的结果；再按需要引导流程、异常、权限、数据、验收、风险与依赖。
- [x] 每轮仅提出一个最关键问题。
- [x] 问题使用小白语言，并给出示例和“不确定，让 AI 建议”。
- [x] 实时展示“我已理解 / 还需要确认 / AI 暂定假设”，将专业字段折叠为可解释的结论。
- [x] 用户跳过时，将补全内容标记为“待确认假设”。
- [x] 输入存在矛盾时，AI 必须澄清后再生成。

### 3.2 先确认骨架，再生成 PRD

- [x] 先生成可编辑的“小白可读方案”：要做什么、给谁用、用户怎样完成、第一版做/不做、成功长什么样、风险与待确认项；同时在后台映射为可交付的 PRD 骨架。
- [x] 用户确认或修改骨架后才允许按节生成。
- [x] 继续保留逐条 Diff 确认和可恢复版本。

### 3.3 结构化章节生成

- [x] 功能需求生成目标、前置条件、主流程、异常边界、输入输出、权限、验收、埋点、待确认假设；向小白展示时优先呈现任务、结果和例外情况。
- [x] 对表格、用户故事、验收等章节输出固定 schema 并本地校验。
- [x] 缺关键字段时提示不可直接交付，不以自然语言篇幅掩盖缺口。

**验收**：未确认假设不伪装为事实；关键业务字段缺失时会明确暴露；生成内容可被后续检测和追溯消费。

**产品决策记录（2026-08-30）**：将阶段 3 从“专业 PRD 填写与生成”调整为“Vibe Coding 前的需求澄清”。指标并非默认必答题；AI 应先帮助用户把愿望说清，再在需要时将其转成可量化目标、优先级、验收和约束。此调整不影响阶段 2 现有交付就绪判定，但阶段 3 实现时必须提供解释、建议和假设确认，不能要求小白理解专业术语。

**执行记录（2026-08-30，第十四轮）**：根据小白/Vibe Coding 定位，AI 产品设计入口改名为“AI 需求澄清 · 从一句想法开始”。首问改为一句自然语言愿望；输入示例同步改为个人健身网页等非专业表达。原先“成功指标”和“约束/竞品”的强制问题改为用户结果和不能接受的情况，系统提示明确禁止强迫填写指标；缺失信息由 AI 输出“AI 建议（待确认）”。阶段 2 的剩余 P1 项暂缓，优先推进阶段 3 的 P0 需求澄清。

**执行记录（2026-08-30，第十六轮）**：需求澄清提示词从固定题序调整为缺口优先：AI 每轮先判断已收集信息中最大的缺口，优先澄清用户/现状、要完成的事、第一版最小范围和不可接受结果；只有会改变方案时才追问权限、数据或技术限制。候选问题仅作为兜底，不能强迫走完五题；每轮仍限制为一个最容易回答的问题。

**执行记录（2026-08-30，第十八轮）**：完成阶段 3 闭环。需求澄清页实时呈现“我已理解 / 还需要确认 / AI 暂定假设”；“不知道”、跳过和 AI 推导均显式保留为待确认，规则检测到“仅自己使用 vs 多人协作”“无需登录 vs 账号成员”“离线 vs 必须联网”等明显矛盾时，提示词要求优先澄清，不能直接汇总。结束澄清后不再直接生成 PRD，而是先打开可编辑的产品方案，用户确认后才启动按节 JSON 草稿生成；原有逐条 Diff 确认和版本回滚保持不变。设计模式下功能需求的固定字段覆盖目标、前置、主流程、异常边界、输入输出、权限、验收、埋点与待确认项；本地校验会明确提示缺口，标记为不宜直接交付。质量基线、既有 85 项 Node 回归和浏览器总览回归 45 项均通过，浏览器无控制台错误。

## 9. 指标与复盘

| 指标 | 定义 |
| --- | --- |
| 激活率 | 首次 10 分钟内创建/导入并处理至少一项问题 |
| 骨架确认率 | 生成骨架后，用户确认或修改并进入章节生成的比例 |
| 首稿可用率 | 用户无需大幅重写即可进入评审的比例 |
| AI 建议有效率 | 被接受或修改后接受的建议占比 |
| 问题关闭率 | 在一次工作流内被处理完成的检测问题比例 |
| 30 日留存 | 激活用户 30 天内再次完成生成、检测、优化或导出 |

## 10. 执行纪律

1. 优先解决 P0，再进入 P1/P2；不得为了新增功能绕过质量基线。
2. 一次只执行一个计划项，完成后更新本文件的状态、验收结果和遗留风险。
3. 所有 AI 写入继续遵循“AI 提议、代码校验、用户确认后写入”。
4. 改动遵循单文件架构和最小修改原则；不引入账号或后端服务，除非产品定位变更。
5. 每次发版同步版本水印、相关文档与测试抽取副本。
