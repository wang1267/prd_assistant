# 产品经理工作台整合计划书

日期：2026-09-08

## 1. 结论与定位

### 最新决定（优先于本文后续旧方案）

2026-09-09 小范围交互修复：按用户要求移除原型页的“工作台 AI 设置”、设置与快捷键速查按钮，AI 配置仍沿用工作台。侧栏拖拽改用 Pointer Capture，不再切换 iframe 的 pointer-events；补齐失焦、取消、捕获丢失及页面清理时的拖拽收尾。真实浏览器验证正常松开、失焦和取消拖动后，HTML 均可通过鼠标滚轮上下滚动。原有键盘快捷键不因移除按钮而取消。

2026-09-09 自然融合修订：原型改为同一窗口内的项目工作区，进入前保存 PRD，返回时定位同一个项目。移除 opener 依赖，所有原型 AI 入口直接读取 `prdKanbanAiSettings`，不建立第二份配置；设置页及导入弹窗的旧 AI 入口改为统一配置/统一 PRD 生成入口。每次生成、优化和说明分析读取本项目最新保存的 PRD、项目上下文，不读取其他项目。共享首次隐私确认与主题。项目名同步；顶栏区分返回文档、页面生成、需求说明和画布编辑。

本轮浏览器验证：无 opener 的同页进入，继承统一模型与地址，请求包含实际 PRD 内容；AI 说明进入需求编辑器并关联到真实元素；画布加载通过。使用受控模型返回，真实服务商质量及大文档压力未验证。原型备份目前仍为独立原型数据备份，尚未声称已完成整个项目的一体备份迁移。

2026-09-09 入口修订：顶部只保留“原型”，不再并列“生成原型 / 我的原型”。点击后进入复用 ProtoReq 的页面工作区，可选择页面、新建页面、导入 HTML，并进入原版画布编辑；PRD 生成放在工作区内。这个模式移除版本、修改记录、分享和账号入口，禁用远程同步。已有 PRD 生成稿首次自动接入，后续新稿作为新页面导入，不覆盖手工编辑页面。

浏览器已验证：单一入口跳转、新建第二页、导入 HTML、原版画布与拖拽组件加载；画布截图检查通过。新增 AI 需求说明与连线接口尚未完成真实服务商联调，不承诺生成质量。AI 读取 PRD 与当前画布元素、文字、位置和尺寸，不是把截图交给视觉模型。复杂整合路线继续暂停。

用户要求不做复杂整合，仅在现有 PMHub 增加原型生成和编辑。

- 已接入：顶部“生成原型”入口，读取当前 PRD、上下文并复用原 AI 配置；生成草稿后可直接改文字、元素字号及文字颜色，也可输入要求让 AI 修改；显式保存、放弃未保存修改、重开恢复、导出 HTML。
- 产品边界：首版为页面视觉原型，不执行原型脚本或连接真实业务；不新增需求绑定、项目体系、统一评论或账号架构。AI 草稿不改写 PRD 正文，不自动覆盖已保存原型。
- 验证：真实浏览器测试使用受控模型返回，已检查真实请求包含 PRD、脚本移除、隔离预览、文字编辑、保存、重开和刷新恢复。尚未使用真实服务商额度验证生成质量。
- 旧 `workbench.html` 和 `src/workbench/` 试验保留但不接入正式入口，也不继续扩展；不删除历史工作。
- 后续仅围绕此功能补齐编辑体验和实际模型质量，不再执行下方大工作台迁移计划。

可以整合，且两者互补：PMHub 解决“需求是否清楚、完整、可交付”，ProtoReq 解决“需求对应哪个页面和交互元素”。推荐形成一个以项目为中心的产品经理工作台。

仍以准备 Vibe Coding 的个人创作者、小白及独立产品经理为首批用户，不转向复杂企业项目管理。专业能力按需展开，不要求新用户先了解 PRD、数据结构或连线规则。

核心路径：用户描述想法或导入材料 → 确认产品方案 → 生成并编辑 PRD → 从已确认需求生成页面原型 → 手动关联原型元素与需求 → 联合评审 → 导出或分享。

最重要的整合原则：**同一个项目、同一份需求、不同工作视图**。不把两个应用并排放在入口，也不让用户维护两套独立的功能描述。

## 2. 现状与可复用能力

| 领域 | PMHub | ProtoReq | 整合决策 |
| --- | --- | --- | --- |
| 想法与方案 | AI 澄清、研究、策略推荐、方案确认、用户命名 | 自然语言生成原型 | 前者确定需求，后者消费已确认需求 |
| 文档 | 项目级章节、结构化条目、导入导出、质量规则 | 页面级自由 Block 编辑器 | 保留项目 PRD，页面视图引用其中的需求 |
| 原型 | 缺少原型编辑与定位 | HTML 导入、AI 生成、交互预览 | 复用原型模块与生成约束 |
| 关联 | 文本关键词推断的需求追溯 | 元素 ID ↔ Block ID 手动绑定、双向定位 | 增加稳定需求 ID；显式关联优先于推断 |
| 评审 | AI 多角色意见同步评论、优化及复核 | Block 评论、回复、解决 | 统一评论目标和来源；保留历史署名 |
| 版本 | 文档/AI 修改及恢复能力 | 页面快照、Block Diff、恢复 | 逐步建立包含文档、页面与关联的项目快照 |
| 存储 | 浏览器 `prdKanbanStateV3` | `protoReq.db.v1`；可选 Python 服务、账号与分享 | 统一存储接口，支持本地优先与可选服务模式 |

两端均使用原生 HTML/CSS/JavaScript，没有为了合并而引入 React/Vue 的必要。ProtoReq 已有 `store/editor/proto/links/ai/app` 模块边界，适合复用；PMHub 主要为单 HTML 文件，适合按整合需要逐步抽取接口。

源码依据：

- `PMHub.html`：`createProject`、`aiState`、`aiDesBuildSkeleton`、`rvSyncReviewComments`、`STORAGE_KEY`。
- `proto-req/js/store.js`：项目/页面/Block/关联/评论/版本模型，`mergeInto`、`replaceBlocks`、页面快照及共享空间。
- `proto-req/js/proto.js`：`srcdoc` 与 `allow-same-origin allow-scripts` 原型执行方式。
- `proto-req/server.py`：账号、分片数据、分享、共享工作区接口及 `merge_db`。

ProtoReq 的 README 与源码存在范围差异，例如源码已有共享工作区路径；实施以源码核实结果为准。此轮未验证线上账号、分享权限及真实模型效果。

## 3. 产品入口与主流程

首页提供“从想法开始 / 导入已有 PRD / 导入原型 / 新建空白项目”，场景模板放入新建流程。导入原型不强制先有完整 PRD，也不自动把所有可点击元素转成需求。

进入项目后，提供四个工作区：

- **项目概览**：当前方案、待确认决定、文档与原型进度、最值得处理的下一步。
- **需求文档**：沿用 PRD 编辑、导入导出、规则检查及 AI 优化。
- **原型与需求**：页面树、交互原型、相关需求；支持手动建立和查看对应关系。
- **评审记录**：统一查看人工/AI 意见、修改及版本，能返回具体需求或页面。

竞品资料归入项目方案上下文，可从概览查看，不新增一个庞大的竞品管理系统。

示例：用户确认“喝水记录工具”首版后，从“每日记录”需求创建记录页面；AI 根据该需求生成原型草稿，用户预览并应用，再把“记录”按钮关联到原需求。修改原需求后，该页面标为“需要核对”，不自动覆盖原型。

## 4. 数据与一致性设计

推荐以 ProtoReq 的模块化结构作为整合应用基础，接入现有 PRD 能力；两份旧项目保留为迁移来源。正式实现前在独立整合分支验证，不直接覆盖任一现有生产入口。

统一存储适配层管理下列对象，避免页面直接读写两套 localStorage：

| 对象 | 关键字段或关系 | 规则 |
| --- | --- | --- |
| Project | ID、名称、schemaVersion、revision | 项目身份统一；用户决定名称 |
| PRD/Section | 文档 ID、章节 ID、原有结构化正文 | 保留旧 PRD 类型与校验所需字段，不先压成纯文本 |
| Requirement | 稳定 ID、章节 ID、内容位置、revision | 被关联的需求拥有稳定身份；正文与页面视图共同修改同一数据 |
| Page | 项目 ID、HTML、所引用需求 ID、来源版本 | 原型只保存需求引用及生成时版本，不维护第二份正文 |
| Binding | 页面 ID、原型元素 ID、需求 ID、状态 | 多对多；明确区分有效、缺元素、缺需求、需核对 |
| Comment | 作者/AI 角色、来源、目标类型和 ID、状态 | 项目/章节/需求/页面均可定位 |
| Snapshot | 需求、原型、关联及版本信息 | 恢复前保存当前状态；恢复后重新校验关联 |
| Research/Decision | 查询、实际来源、研究结论、用户决定 | 区分已确认、AI 建议、未核实信息；按项目保存 |

第一轮仅支持用户选定的功能条目或独立 Block 建立稳定需求 ID，不急于让任意跨段落选区都成为可绑定对象。页面专属需求也通过该接口新增至 PRD 对应章节。

发生删除、原型替换或恢复时，先说明受影响的关联；允许撤销或重新绑定。绝不仅凭相似文字把旧关联自动认定为正确。AI 原型修改尽量保留 `data-proto-id`，应用前比较新增、缺失及重复 ID。

## 5. AI 整合

统一配置、请求状态、停止、超时和失败重试入口；按任务使用标准、快速、深度模型。原型生成额外使用需求 ID、页面目标、边界与交互状态作为输入。

- 从想法开始：默认给推荐，保留手动输入；研究后展示资料链接，三个赛道各自融合产品方向、复用与差异化。用户已选方向后围绕剩余决策收敛，避免每轮推翻定位。
- PRD → 原型：先确认页面范围，再生成草稿、预览、应用；失败保留原页面。
- 原型 → PRD：首期只允许用户选择页面后请求“补充需求建议”，用户确认才写入，不把原型表现直接当成真实业务规则。
- 联合评审：既检查 PRD 缺口，也指出需求已变但原型尚未核对、关联目标缺失等问题。未做静态/运行验证时，不声称原型行为满足验收。
- Skill 可作为流程规范来源；需转成应用可执行的提示词、状态和工具接口，不能仅复制 SKILL.md 就声称网页拥有搜索和记忆能力。

## 6. 存储、服务与直接相关风险

**本地模式**：保留无账号编辑，统一数据推荐存 IndexedDB，localStorage 仅存轻量偏好；原型 HTML、版本和文档容易超过现有 localStorage 容量。迁移失败保留原数据与备份，不能静默重置空库。

**服务模式**：复用 Python 服务作为起点。合并后的数据模型需同步修改前后端复制、导入、分享及合并函数。首期用 revision 冲突检测和“保留副本/重新加载”处理并发，避免按整项目时间戳直接覆盖；不承诺实时协作。账号模式连不上服务时保留待同步状态，不静默切换成另一套本地项目。

**AI 密钥**：两个现有前端均有浏览器 Key 配置。整合后 AI 调用经可选本地/服务器代理处理凭据，前端仅保存配置标识；纯静态模式仍可编辑及导出，AI 需连接代理。不得把共享密钥放入发布文件，服务端自定义上游地址也需有允许范围与超时限制。

**原型执行隔离**：目前同源 iframe 同时允许脚本执行，导入或 AI 生成的脚本可能接触宿主页面。与账号、PRD 合并前必须隔离：建议使用不带 `allow-same-origin` 的沙箱与受控消息通道，复用圈选逻辑但改为在沙箱内采集定位信息。验证消息来源、会话标识与消息结构，不接受任意宿主操作。验收应证明原型不能读取工作台文档、凭据或调用宿主受保护接口。

**分享边界**：服务端强制校验只读/编辑权限与分享范围。首期优先复用只读分享，明确本地链接不能跨设备读取本地数据；同项目协作编辑后置。

这使旧计划“不做账号”的边界变为“本地模式不要求账号，服务分享可选账号”；旧 ProtoReq“AI 不写需求”的边界变为“AI 可提出需求草稿，用户确认后写入”。这些是本次整合提案，不提前修改旧产品行为。

## 7. 分阶段实施与验收

### 阶段一 · P0：最小整合验证

- [ ] 选定一个旧 PRD 项目和一个 ProtoReq 示例，建立统一项目模型与存储适配层。
- [x] 建立需求 ID 与页面引用，将一条 PRD 需求显示到原型侧并可回到正文（独立体验项目验证）。
- [ ] 完成原型沙箱隔离验证，以及文档→生成草稿→应用→手动关联的一页闭环。
- [ ] 明确模型代理部署与凭据配置方式。

验收：同一需求在两个视图显示一致；改名不失联；删需求/换原型会报告关联影响；原型不能访问宿主数据。若这一阶段做不到，不扩大到全功能迁移。

### 阶段二 · P0：可用的本地工作台

- [ ] 统一项目入口、页面导航与 AI 配置；迁入现有 PRD 编辑、生成、检测与导出。
- [ ] 迁入原型导入、生成、圈选、手动连线、定位与撤销。
- [ ] 从两种旧备份导入，提供预览、来源 ID 映射、重复导入识别及恢复点。
- [ ] 非无损转换的富文本/表格保留原内容并提示人工核对，不静默丢弃。

验收：两类已有项目都能导入、刷新恢复、编辑并导出；迁移不会修改源库；从想法到带需求关联原型走通。原型较大的项目保存失败时能重试或导出。

### 阶段三 · P1：评审与变更一致性

- [ ] 统一人工评论与带角色的 AI 评审，保留旧评论与来源。
- [ ] 加入“需求变更后原型待核对”、失效关联列表及重新绑定。
- [ ] 引入项目快照、恢复前备份及文档/原型/关联同步恢复。
- [ ] AI 优化先预览影响，仅应用用户确认且通过校验的改动。

验收：任一评审意见可定位；恢复后内容与关联版本一致；AI 修改不覆盖用户锁定内容；冲突提示不伪装为已同步。

### 阶段四 · P1：可选服务与分享

- [ ] 服务存储适配统一模型，补齐 revision 冲突检测、账号隔离与分享范围。
- [ ] 完成登录、退出、网络失败、只读访问、分享撤销与跨设备查看的定向验证。
- [ ] 使用独立测试数据部署；验证通过后再制定旧站迁移及回滚步骤。

验收：跨设备能看到授权范围内的完整文档与原型；只读用户不能改写；两端并发修改不会无提示丢失；停用服务器后本地编辑模式仍可用。

### 后续 P2 / 暂缓

P2：GitHub 项目深度核验、原型与验收规则的辅助检查、更多页面模板。  
暂缓：AI 自动连线、多人实时光标、复杂审批、任务排期、Jira 双向同步、React/Vue 源码导入和全面替换编辑器。

## 8. 验证与试用标准

每阶段只跑直接相关验证：需求绑定与迁移用小样本回归；沙箱、账号和分享必须验证权限边界；编辑/恢复用浏览器实际操作；模型先使用可控返回验证流程，再用真实账号验证生成质量，不能把模拟测试当作服务商联调。

建议试用任务：“创建一个简单产品 → 确认 PRD → 生成一个页面 → 建立两条关联 → 修改一条需求 → 查看影响 → 导出或分享”。记录完成率、用时、重复编辑次数、失联次数及主观困难，不预先承诺留存超过 70%。

第一阶段重点只有三件：统一需求身份、走通一页原型闭环、确保数据和执行环境隔离。通过后再估算完整迁移工作量。
